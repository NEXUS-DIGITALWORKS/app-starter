# リリース前・フルコードレビュー指示

このリポジトリ全体に対して、**セキュリティ・保守性・品質・パフォーマンスの観点から総合的なコードレビュー**を行ってください。

リリース前の確認を想定しているため、ソースコードだけでなく、依存パッケージ、設定ファイル、DB設定、CI/CD、認証・認可、テスト等もレビュー対象としてください。

今回は原則として**レビューのみ**を行い、コードの修正はまだ行わないでください。

問題点を一覧化した後、私の確認を取ってから修正に着手してください。

---

## 1. レビュー方針

- リポジトリ全体の構成を最初に把握する
- 主要な実行経路・データフロー・認証フローを確認する
- ソースコードだけでなく設定ファイルや依存関係も確認する
- 問題の可能性だけで「脆弱性」と断定しない
- 実際のコード・設定・依存関係を根拠として指摘する
- 判断できない場合は「要確認」と明記する
- 過剰なリファクタリングは提案しない
- 現在の仕様・動作を可能な限り維持する
- セキュリティ上重大な問題を最優先する
- 修正によるデグレードの可能性も考慮する
- 自動修正は私の承認後に行う

---

# 2. セキュリティ・脆弱性チェック

OWASP Top 10および一般的なWebアプリケーションのセキュリティベストプラクティスを基準に確認してください。

## インジェクション

- SQL Injection
- Command Injection
- XSS
- HTML Injection
- Template Injection
- LDAP / XPath等のInjection
- OSコマンド実行

外部入力が文字列結合等によってSQL・コマンド・HTML等へ直接渡されていないか確認してください。

## 認証・認可

- 未認証ユーザーによるアクセス
- 権限チェック不足
- IDOR
- 管理者機能へのアクセス制御
- API側での認可不足
- フロントエンドだけで権限制御していないか
- ロール・ユーザーIDなどをクライアント入力だけで信用していないか
- セッション固定・セッション管理不備
- JWT検証不備

Supabaseを使用している場合は特に以下を確認してください。

- RLSが適切に設定されているか
- RLSを前提としたコードになっているか
- service_roleキーがフロントエンドへ露出していないか
- anon/publicキーと秘密鍵を正しく区別しているか
- StorageのPolicyが適切か
- RPC / Functionで権限を迂回できないか

## 機密情報

以下がソースコードへハードコーディングされていないか確認してください。

- APIキー
- パスワード
- Access Token
- Refresh Token
- JWT
- DB接続情報
- Secret Key
- Private Key
- service_roleキー
- Webhook Secret
- AWS/GCP等のCredential

以下も確認してください。

- `.env`
- `.env.*`
- 設定ファイル
- テストコード
- サンプルコード
- README
- CI/CD設定
- Git管理対象ファイル
- `.gitignore`

可能であれば、Git履歴に過去の秘密情報が残っていないかも確認してください。

## 入力値

外部から受け取る以下の入力を確認してください。

- URL parameter
- Query parameter
- Form
- JSON
- Header
- Cookie
- ファイルアップロード
- APIリクエスト
- Webhook

確認事項：

- 型チェック
- 必須チェック
- 長さ制限
- 値の範囲
- 許可リスト
- サニタイズ
- ファイルタイプ
- ファイルサイズ
- MIME type
- 拡張子

## その他の脆弱性

以下も確認してください。

- SSRF
- CSRF
- Path Traversal
- Open Redirect
- Insecure Deserialization
- Prototype Pollution
- Race Condition
- ReDoS
- 不適切なCORS
- Cookie設定不備
- ファイルアップロード脆弱性
- 任意ファイル読み込み
- 任意ファイル書き込み
- 不適切な暗号化
- HTTP通信による機密情報送信
- セキュリティヘッダー不足
- Rate Limit不足
- Abuse対策不足

# 3. 依存パッケージ・Supply Chain

使用しているPackage Managerを判定してください。

例：

- npm
- pnpm
- yarn
- pip
- poetry
- uv
- Maven
- Gradle

以下を確認してください。

- 既知のCVE
- Critical / High vulnerability
- Deprecated package
- 長期間更新されていないパッケージ
- 不要な依存パッケージ
- development dependency / production dependencyの誤分類
- バージョン固定状況
- lockファイルの有無
- 不審なpostinstallスクリプト
- Typosquatting等、不審な依存関係の可能性

利用可能であれば、プロジェクトに適した監査コマンドを実行してください。

例：

```bash
npm audit
npm outdated
```

脆弱性が検出されたからという理由だけで、安易にmajor versionへアップデートしないでください。

アップデートによる互換性リスクも合わせて報告してください。

# 4. エラーハンドリング・情報漏洩

以下を確認してください。

- Stack Traceをユーザーへ返していないか
- 内部ファイルパスが表示されないか
- SQLエラーがそのまま表示されないか
- DB情報が含まれないか
- APIキーなどがエラーメッセージへ含まれないか
- 開発用debug情報が本番環境で有効になっていないか

ユーザー向けエラーメッセージと内部ログが適切に分離されているか確認してください。

# 6. コード品質・可読性

## 重複

- 重複コード
- コピー＆ペーストされた処理
- 同じロジックの複数実装
- DRY原則から大きく逸脱している部分

## 複雑度

- 長すぎる関数
- 長すぎるコンポーネント
- 深すぎるネスト
- 条件分岐が多すぎる処理
- 責務が多すぎるクラス・関数・コンポーネント

必要に応じて関数分割、Hook化、Utility化、Service化、Component分割などを提案してください。

ただし、不必要な細分化は避けてください。

## 命名

- 意味の分からない変数名
- tmp / data / valueなど曖昧すぎる名前
- 関数の責務と名前が一致していない
- booleanなのに状態が分かりにくい名前
- プロジェクト内で命名規則が統一されていない

## デッドコード

- 未使用import
- 未使用変数
- 未使用関数
- 未使用component
- 到達不能コード
- コメントアウトされた古いコード
- 不要なconsole.log
- デバッグコード

- 責務分離

- 不要なループ
- 二重・三重ループ
- 同じ計算の繰り返し
- 同じAPIへの不要な複数アクセス

# 16. 出力形式

重大度の高い順に以下で分類してください。

1. Critical
2. High
3. Medium
4. Low
5. Info

最初にサマリーを表示してください。

```text
レビュー結果

Critical : X件
High     : X件
Medium   : X件
Low      : X件
Info     : X件
```

続けて「最優先で修正すべき項目」を最大5件表示してください。

各問題について必ず以下を記載してください。

| 項目 | 内容 |
|---|---|
| ID | SEC-001 / QUALITY-001 等 |
| 重大度 | Critical / High / Medium / Low / Info |
| カテゴリ | Security / Quality / Performance / Maintainability 等 |
| ファイル | 対象ファイル |
| 行番号 | 対象行 |
| 問題 | 何が問題なのか |
| 根拠 | なぜ問題なのか |
| 影響 | 何が起こる可能性があるか |
| 修正案 | 推奨する修正方法 |
| コード例 | 必要な場合のみ |
| 修正リスク | デグレード可能性・影響範囲 |

# 17. 指摘しないもの

以下は原則として問題としてカウントしないでください。

- 単なる好みのコーディングスタイル
- 動作に影響しない細かな表記
- メリットの小さい過剰なリファクタリング
- 根拠のない将来的懸念
- 実際には到達できない攻撃経路
- 利用しているライブラリ内部そのもののコード品質

重要な問題に集中してください。

# 18. 修正フェーズ

レビュー完了時点ではコードを変更しないでください。

最後に以下の形式で修正候補を一覧化してください。

```text
修正候補

[ ] SEC-001
[ ] SEC-002
[ ] QUALITY-001
```

私が修正対象を指定してからコード変更を開始してください。

修正時は以下を守ってください。

- 既存機能を維持する
- 不要な仕様変更をしない
- 修正範囲を最小限にする
- セキュリティ修正による別の脆弱性を作らない
- lint
- typecheck
- test
- build

を可能な範囲で実行してください。

修正完了後は、変更差分を再レビューし、以下を報告してください。

- 修正した問題
- 変更したファイル
- テスト結果
- build結果
- 残存リスク
- 未対応項目
