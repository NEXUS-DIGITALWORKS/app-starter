# 日常・差分コードレビュー指示

このリポジトリについて、**今回変更されたコード（Git差分）を中心に、セキュリティ・保守性・品質・パフォーマンスの観点からコードレビュー**を行ってください。

今回は原則として**レビューのみ**を行い、コードの修正はまだ行わないでください。

問題点を一覧化した後、私の確認を取ってから修正に着手してください。

---

## 1. レビュー対象

まずGitの状態と差分を確認し、今回追加・変更されたファイルを特定してください。

必要に応じて、変更箇所から参照される既存コードも確認してください。

例：

```bash
git status
git diff
git diff --staged
```

コミット済みの変更をレビューする場合は、適切な比較元を判断して差分を確認してください。

### レビュー方針

- 今回の変更箇所を最優先で確認する
- 関連する既存コードも必要に応じて確認する
- 問題の可能性だけで「脆弱性」と断定しない
- 実際のコード・設定・依存関係を根拠として指摘する
- 判断できない場合は「要確認」と明記する
- 単なる好みのコーディングスタイルは原則として指摘しない
- 過剰なリファクタリングは提案しない
- 現在の仕様・動作を可能な限り維持する
- 修正によるデグレードの可能性も考慮する
- 自動修正は私の承認後に行う

---

## 2. セキュリティチェック

OWASP Top 10および一般的なWebアプリケーションのセキュリティベストプラクティスを基準に、今回の変更によって新たな脆弱性が入り込んでいないか確認してください。

特に以下を確認してください。

### インジェクション

- SQL Injection
- Command Injection
- XSS / HTML Injection
- Template Injection
- OSコマンド実行
- 外部入力をSQL・コマンド・HTML等へ直接渡していないか

### 認証・認可

- 未認証ユーザーによるアクセス
- 権限チェック不足
- IDOR
- 管理者機能へのアクセス制御
- API側での認可不足
- フロントエンドだけで権限制御していないか
- ロールやユーザーIDをクライアント入力だけで信用していないか

Supabaseを使用している場合は以下も確認してください。

- RLSを前提とした安全な実装になっているか
- service_roleキーがフロントエンドへ露出していないか
- anon/publicキーと秘密鍵を正しく区別しているか

### 機密情報

今回の変更に以下がハードコーディングされていないか確認してください。

- APIキー
- パスワード
- Access Token / Refresh Token
- JWT
- DB接続情報
- Secret Key
- Private Key
- service_roleキー
- Webhook Secret
- AWS / GCP等のCredential

`.env`、設定ファイル、テストコード、README等も必要に応じて確認してください。

### 入力値

追加・変更された入力処理について以下を確認してください。

- 型チェック
- 必須チェック
- 長さ制限
- 値の範囲
- 許可リスト
- サニタイズ
- ファイルタイプ
- ファイルサイズ
- MIME type
- 拡張子

### その他

- SSRF
- CSRF
- Path Traversal
- Open Redirect
- Insecure Deserialization
- Prototype Pollution
- Race Condition
- ReDoS
- 不適切なCORS
- Cookie設定不備
- JWT検証不備
- セッション管理不備
- ファイルアップロード脆弱性
- 任意ファイル読み書き

## 3. エラー・ログ

変更箇所について以下を確認してください。

### エラーハンドリング

- Stack Traceをユーザーへ返していないか
- 内部ファイルパスを表示していないか
- SQLやDBの内部エラーをそのまま返していないか
- APIキー等がエラーへ含まれていないか
- 開発用debug情報が本番環境へ露出しないか

### ログ

以下を不用意に出力していないか確認してください。

- パスワード
- Token
- Authorization Header
- Cookie
- API Key
- クレジットカード情報
- メールアドレス
- 電話番号
- 氏名
- 住所
- その他個人情報・機密情報

不要な `console.log` やデバッグログも確認してください。

---

## 4. コード品質・保守性

今回の変更を中心に以下を確認してください。

- 重複コード
- 不要なコピー＆ペースト
- 長すぎる関数・コンポーネント
- 深すぎるネスト
- 条件分岐が多すぎる処理
- 責務が多すぎる関数・クラス・コンポーネント
- 曖昧または不適切な命名
- 未使用import
- 未使用変数・関数
- 到達不能コード
- コメントアウトされた古いコード
- Magic Number / Magic String
- 型定義の重複
- API処理やDB処理の不必要な分散
- 循環依存
- 不要な密結合

必要に応じて関数分割、Hook化、Utility化、Service化、Component分割等を提案してください。

ただし、メリットの小さい細分化は行わないでください。

---

## 5. TypeScript / React

TypeScriptを使用している場合：

- `any` の乱用
- `as any`
- `as unknown as`
- 不要な型アサーション
- `!` Non-null assertionの乱用
- nullable値の扱い
- APIレスポンスの型安全性
- DBデータとの型不整合

Reactを使用している場合：

- useEffectの依存配列
- 不要なuseEffect
- 無限レンダリング
- 不要な再レンダリング
- stateの重複
- derived state
- keyの不適切な指定
- 巨大コンポーネント
- Event Listener解除漏れ
- APIリクエスト競合
- loading / error状態
- `dangerouslySetInnerHTML`

---

## 6. パフォーマンス・非同期処理

以下を確認してください。

- 不要なループ
- 不要な二重・三重ループ
- 同じ計算の繰り返し
- 同じAPIへの不要な複数アクセス
- 不要なDBアクセス
- N+1
- 大量データの一括取得
- 不要なReact再レンダリング
- メモリリーク
- await漏れ
- Promiseの握りつぶし
- Promise.allが適切な箇所の逐次処理
- 過剰な並列処理
- try/catch不足
- タイムアウト不足
- Race Condition

実害がほぼないマイクロ最適化は指摘不要です。

---

## 7. テスト・自動チェック

プロジェクトに存在するコマンドを確認し、可能な範囲で以下を実行してください。

- lint
- typecheck
- test
- build

存在しないコマンドを勝手に作らないでください。

今回の変更に対してテストが不足している場合は、追加すべきテストケースを提案してください。

---

## 8. 出力形式

最初にサマリーを表示してください。

```text
レビュー結果

Critical : X件
High     : X件
Medium   : X件
Low      : X件
Info     : X件
```

続けて「最優先で修正すべき項目」を最大5件表示してください。

各問題について以下を明記してください。

| 項目 | 内容 |
|---|---|
| ID | SEC-001 / QUALITY-001 等 |
| 重大度 | Critical / High / Medium / Low / Info |
| カテゴリ | Security / Quality / Performance / Maintainability 等 |
| ファイル | 対象ファイル |
| 行番号 | 対象行 |
| 問題 | 何が問題なのか |
| 根拠 | なぜ問題なのか |
| 影響 | 何が起こる可能性があるか |
| 修正案 | 推奨する修正方法 |
| コード例 | 必要な場合のみ |
| 修正リスク | デグレード可能性・影響範囲 |

---

## 9. 修正フェーズ

レビュー完了時点ではコードを変更しないでください。

最後に以下の形式で修正候補を一覧化してください。

```text
修正候補

[ ] SEC-001
[ ] SEC-002
[ ] QUALITY-001
```

私が修正対象を指定してからコード変更を開始してください。

修正時は以下を守ってください。

- 既存機能を維持する
- 不要な仕様変更をしない
- 修正範囲を最小限にする
- lint / typecheck / test / build を可能な範囲で実行する
- 修正後に差分を再レビューする
